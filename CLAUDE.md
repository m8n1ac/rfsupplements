# RF Supplements Ops CRM

Private operations CRM at **https://ops.rfsupplements.com**, running on the same
box as the WooCommerce store it mirrors.

**The spec is the source of truth:** `/home/ubuntu/incoming/rfs-ops-crm-spec.md`.
Phase 0 findings and the decisions taken on them:
`/home/ubuntu/rfs-discovery/DISCOVERY.md`. Read both before changing behaviour;
this file only records what those two do not, or what has since changed.

Work one phase at a time. At the end of a phase, stop, report against that
phase's gate checklist, and wait for approval. Engineering rules are spec §2 —
simple over complex, one way to do each thing, no fallbacks, fail fast, surgical
changes, TypeScript strict.

## Hard boundaries

- **Never touch rfsrx.com** — its files, database, vhost or FPM pool. It shares
  this host and runs as a separate `rfsrx` user. The `rfs_crm` database user is
  denied both WordPress schemas; `SELECT` against either returns `ERROR 1142`.
  Keep it that way.
- **WordPress changes are limited to spec §7**: the `crm-sync` user and its
  Application Password, the `rfs-crm-bridge` mu-plugin, and `wp rfs-crm backfill`.
  Nothing else. The CRM never reads WordPress tables directly — everything goes
  through the REST API.
- WooCommerce is the system of record for store data. The CRM owns only notes,
  tasks, tags, inquiries and assignments.
- **The WordPress timezone must stay UTC.** Woo Analytics groups by it, and the
  Gate 4 comparison depends on it (Gate 0, A2).


```
npm run fixtures:store -- --create|--remove   # the store's test order/product/customer
sudo /usr/local/sbin/rfs-crm-backup.sh run|restore-test|latest
```

Service: `rfs-crm`, running as the **`rfs-crm` system account** (no login shell)
with secrets in `/etc/rfs-crm/env`, not in the app directory. Deploys still run
as `ubuntu`, which is why `/opt/rfs-crm` is group-readable by `rfs-crm` and
`deploy.sh` re-applies that after every build.

Timers: `rfs-crm-sync.timer` (60s), `rfs-crm-sync-full.timer` (11:30 UTC = 04:30
Pacific) and `rfs-crm-backup.timer` (04:10 UTC), all clear of the existing
`rfs-backup` (03:13) and `rfs-snapshot` (03:45).

The operator runbook is `README.md`: deploy, add a user, rotate the app
password, run a sync, restore a backup.

## Things that will bite you

- **The project is ESM** (`"type": "module"`). Prisma 7's generated client uses
  `import.meta`, so CJS tooling cannot load it.
- **`server-only` breaks anything outside Next's bundler.** Every tsx entry point
  and both test runners set the `react-server` condition, which maps it to an
  empty module. Forgetting this took the sync worker down for nine minutes —
  see the commit. Keep it on every new script.
- **`src/lib/env.ts` throws at import and is server-only.** A client component
  that imports it crashes the page in the browser. Pure constants a client
  component needs live in their own module — `src/lib/order-status.ts` is the
  pattern, not `src/lib/format.ts`, which reads `STORE_TZ`.
- **Prisma 7 moved the connection URL out of `schema.prisma`** into
  `prisma.config.ts`, and the client needs the MariaDB driver adapter.
  `migrate dev` needs the `rfs_crm_shadow` database; `migrate deploy` does not.
- **`LayoutProps` / `PageProps` are generated by `next build`.** `tsc --noEmit`
  fails on a new route until you have built once.
- **shadcn's `CardTitle` renders a `div`, not a heading.** Test selectors use
  `getByText`; only `PageHeader` emits a real `h1`.
- **A generated shadcn component can be wrong.** `CommandDialog` shipped without
  its `Command` wrapper, so ⌘K threw on open. These files are vendored — fix
  them in place and say why in a comment.
- **The e2e suite pauses `rfs-crm-sync.timer`** (`tests/e2e/global-setup.ts`).
  The stale-write tests need the CRM's copy to stay older than the store's, and
  a 60-second sync repairs exactly that. Stopping the timer does not stop a run
  already in flight, so it waits for one.
- **MariaDB's root uses unix_socket auth.** Passing `-h 127.0.0.1` forces TCP and
  the socket plugin never applies, so admin commands must omit `-h`.
- **Three dependency overrides**, all in `package.json` so `npm ci` reproduces
  them: `nodemailer` held forward past its advisories, `mysql2` pulled to a
  patched 3.24, and `mariadb` pinned to `~3.4.7` because
  `@prisma/adapter-mariadb` pins exactly 3.4.5, which carries three advisories.
  `npm audit` is clean; keep it that way.

## Auth

Email and password only. **TOTP was cancelled by Darrin on 2026-09-17** and
removed rather than disabled, so spec §9's 2FA language no longer applies. The
5-attempt / 15-minute lockout and the nginx `limit_req` on `/api/auth/` are the
only brute-force defences — keep both.

There is no self-signup. Admins create users, who set their own password on a
single-use invite link. `requireUser(role?)` reloads from the database and
interrupts with `redirect()` or `forbidden()`, so callers need no try/catch and
a page cannot render for the wrong user. Every page, action and route handler
calls it. STAFF must never receive revenue data — enforce on the server; there
are tests asserting it is absent from the HTML, not merely hidden.

## Sync

Pull-based, cursor per resource, advanced only after a page commits, so a killed
run resumes where it stopped. Order matters: products, customers, orders,
refunds, submissions.

- **Customers have no `modified_after`** on this Woo build, hence the two-step
  route in §6.1. Use Woo's default role filter; `role=all` drags in admins and
  affiliates, who are not customers.
- **Refunds are found from the summary already on each order**, so only orders
  that have one are fetched — 3 requests, not 557.
- **A full run marks absent records `deletedInWoo` and never hard-deletes.** An
  empty Woo response means "nothing to compare", not "delete everything".
- **A crash before `startRun` leaves no `SyncRun` row**, so the three-strikes
  alert cannot fire. Settings → Sync flags any resource with no success in 15
  minutes; that is the signal that catches it.
- **Fixtures are generated, not hand-kept.** The Phase 0 fixtures did not match
  the live API and quietly invalidated the tests. Test assertions derive their
  expected values from the fixture.

## Metrics

`src/lib/metrics/` is the single source. Timezone is always an argument: the UI
passes `STORE_TZ`, the Gate 4 check passes UTC.

- **Basis is `paidAtWoo`**, excluded statuses are pending / failed / cancelled.
  Verified, not assumed: on a created-date basis August 2026 returns 244 orders
  against Woo's 53.
- gross = Σ line-item subtotals · net = gross − coupons − refunds ·
  total = net + shipping + tax · AOV = net ÷ counted orders. Refunds count on the
  refund's own date.
- `npm run verify:metrics` compares five windows against Woo's Analytics REST
  API and, on a mismatch, names the offending orders.
- **Known open issue:** Woo's Analytics lookup tables have drifted from its own
  orders. Order 2285 is counted by Analytics but returns 404; order 2548 has a
  $56.97 total and zero line items; order 2403 shows $5,000 gross and $5,000
  discount live but 0/0 in the lookup. August matches to the cent; the year does
  not. The fix is WooCommerce → Status → Tools → *Regenerate reports data*, which
  is Darrin's to run. Do not "fix" `src/lib/metrics/` to match stale tables.

## Charts

The stock shadcn chart tokens are greyscale and cannot carry categorical
identity; `--chart-1..5` hold steps validated for both surfaces. One y-scale
always — never a second axis. A legend only when there are two or more series.
Slot 3 is below 3:1 on the light surface, so charts using it ship the value table
beside them.

## Outbound writes

Only three are allowed (spec §6.2): order status, order notes, customer contact
fields. All go through `src/lib/woo/write.ts`, which is Woo-first: read and
refuse if the store is newer, write to Woo, store Woo's response, audit it. A
failure writes nothing locally — no queue, no retry.

`src/lib/woo/order-emails.ts` records which statuses email whom, read from this
store's settings: processing, completed, on-hold and refunded reach the
**customer**; cancelled and failed reach the three **owner** addresses. Keep it
accurate if the store's email settings change — the confirm dialog quotes it.

Customer email is never editable (it is the store login). Guest contacts have no
Woo record and are edited locally only.
